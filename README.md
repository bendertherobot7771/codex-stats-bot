# Codex Stats Bot

Codex Stats Bot собирает статистику использования Codex с нескольких Windows-компьютеров и показывает сводку через Telegram-бота, запущенного на Orange Pi или другом Linux-сервере.

Первый рабочий MVP включает Windows-агент, HTTP-сервер, SQLite и Telegram-бота.

Текущая версия: `0.4.0`.

## Цели

- автоматически определять начало и завершение задания Codex;
- считывать недельный процент до и после задания через текущую локальную авторизацию Codex;
- показывать остаток недельного лимита до/после задания и накопленный расход ПК;
- связывать расход с пользователем и компьютером;
- корректно обрабатывать параллельные задания;
- хранить статистику централизованно и показывать её через Telegram.

## Архитектура

Проект состоит из двух частей:

1. Windows-агент следит за локальными JSONL-журналами Codex, распознаёт события `task_started`, `token_count` и `task_complete`, получает снимки недельного окна и отправляет обезличенную статистику серверу.
2. Сервер на Orange Pi принимает идемпотентные события по HTTP, сохраняет их в SQLite, рассчитывает распределение недельного расхода и отвечает на команды Telegram-бота.

OAuth-токен Codex используется только локальным агентом для запроса текущего лимита и никогда не отправляется на сервер. Тексты запросов, ответы модели и результаты инструментов не собираются.

Агент сначала запрашивает свежий снимок недельного окна через `https://chatgpt.com/backend-api/wham/usage`, используя `~/.codex/auth.json`. Это внутренний, официально не документированный интерфейс Codex, который может измениться. При ошибке агент использует последний снимок из локального журнала с явной отметкой источника.

## Параллельные задания

Сервер восстанавливает хронологию снимков **общего аккаунта**, а не складывает разницы отдельных заданий. Каждый прирост расхода между замерами учитывается один раз. Если работал один ПК, прирост относится к нему; если несколько — распределяется пропорционально времени активности каждого ПК в этом интервале. При одинаковом времени доли равны. Несколько задач на одном ПК не увеличивают его вес. Токены не используются для распределения и не показываются в Telegram; старые поля токенов сохраняются в БД и JSON API для совместимости.

Доли округляются до сотых процента методом наибольших остатков: даже сумма отображаемых долей не превышает исходный расход. **Сумма счётчиков всех ПК одного аккаунта за один период между сбросами не превышает 100%.** Часть расхода без достоверно наблюдавшейся активности показывается отдельно и не приписывается следующему включённому ПК.

Пересечения — оценка, не точное измерение. Округление лимита OpenAI, задержки его обновления, рассинхронизация часов и работа без агента ограничивают точность. Часы всех ПК должны синхронизироваться. Незавершённое задание без событий больше 120 секунд перестаёт участвовать в распределении новых интервалов: зависшая запись не должна навсегда получать чужой расход. Доставка позднего heartbeat/завершения может восстановить интервал. Для уведомления используется состояние на момент обработки; поздняя доставка событий может пересчитать историю и доли, но ранее отправленное сообщение не редактируется.

### Сбросы и история

Агент получает свежие замеры при старте/завершении, каждые 30 секунд во время работы и каждые 5 минут в простое (интервалы ориентировочные, зависят от сети). При смене `reset_at` открывается новый период. Внеплановый сброс с прежним `reset_at` определяется по **двум последовательным свежим API-замерам ниже предыдущего максимума**: один отстающий ответ не должен обнулить статистику всех ПК. Подтверждённый сброс обнуляет текущие счётчики всех ПК аккаунта; прежние периоды остаются в `/weeks` и `/week N`.

Агент не продлевает heartbeat задания, в журнале которого более 10 минут нет событий. Это защищает от старых зависших заданий после перезапуска; долгое выполнение инструмента без записей может временно перестать считаться активным, а последующее событие восстановит учёт. Старые записи не удаляются.

Если за календарную неделю были внеплановые сбросы, сумма исторических периодов может превышать 100%, но текущий период — нет. Задание, пересёкшее сброс, учитывается раздельно по периодам; отрицательный расход не создаётся. Расход между последним замером и фактическим сбросом, а также до первого замера нового периода невозможно восстановить: первый замер становится базовой точкой, а не выдуманным расходом. Если все агенты выключены, сервер узнает о сбросе только после их запуска. Сброс, который полностью скрыт ростом расхода между двумя замерами, обнаружить по процентам нельзя.

События хранятся без удаления, повторная доставка не дублирует расход. История пересчитывается по новому алгоритму; старые записи без достоверного времени снимка/недельного окна не превращаются в якобы точные проценты. Свежий API-снимок, полученный более чем через 30 секунд от границы задания, не используется как замер этой границы. Если доступны прямые API-замеры аккаунта, журнал не подмешивается в их хронологию и не может вызвать ложный сброс.

### Формат уведомлений

```text
GamePC · 25% за неделю · До сброса 3д 2ч · Сброс 1 на 14д 2ч
До задания: 80% >>> После задания: 76%
Изменение за время задания: 4% Учтено за GamePC: 4%
```

В первой строке — расход ПК за текущий период, во второй — **остаток** общего недельного лимита. При пересечениях учтённая доля помечается `≈`, добавляется текст:

```text
Во время задания также работал WorkPC.
Расход пересечения распределён между ПК оценочно.
```

Для задания через сброс вместо отрицательной разницы выводится `сброс/смена окна`; «Учтено» относится к текущему периоду. Если нет замера — это явно указано. Команды статистики также показывают время до сброса. Таймер вычисляется при формировании сообщения, уже отправленный текст не является живым таймером.

Количество и сроки внеочередных сбросов читаются локально через GET `https://chatgpt.com/backend-api/wham/rate-limit-reset-credits`. Передаются только количество и даты истечения, без идентификаторов кредитов. Разные сроки показываются отдельно. При нуле/истечении срока строка скрывается; при недоступном сроке выводится `срок неизвестен`. Ошибка этого необязательного запроса не блокирует учёт недельного лимита. Агент **никогда не расходует сбросы**. Оба endpoint внутренние и могут измениться. Только окно ровно 10080 минут считается недельным; пятичасовое окно и отдельные лимиты других моделей игнорируются.

## Windows-агент

### Подключение из интернета (HTTPS 28443)

Внешний адрес: `https://79.134.223.90:28443`. На Keenetic пробрасывается только TCP 28443 на Orange Pi `192.168.32.125:28443`. Вход обслуживает отдельный `server/nginx-codex-stats.conf`; он передаёт запросы на `127.0.0.1:8765`. Порт 443 не используется. Nextcloud остаётся на 18443; его конфигурация и ограничения по странам не применяются к статистике. При смене внешнего IP потребуется обновить адрес и сертификат.

Существующие домашние агенты продолжают использовать `http://192.168.32.125:8765`; их настройки не меняются. `CODEX_STATS_PUBLIC_URL=https://79.134.223.90:28443` определяет адрес в новых инструкциях `/addpc`, но не перенастраивает установленные устройства. Если новый ПК будет работать только дома, адрес в установочной команде можно заменить локальным.

Наружу доступны только GET `/health` и POST `/api/v1/enroll`, `/api/v1/events`, `/api/v1/agent/checkin`. Статистика просматривается через Telegram; `/api/v1/stats`, административный API и все прочие маршруты снаружи закрыты. Nginx auth_request допускает к событиям/check-in только индивидуальные ключи зарегистрированных устройств. Общий ключ сервера не принимается. Внутренний `/api/v1/public-auth` доступен только через loopback, никогда через публичный location. Требуется сервер 0.4.2 или новее; со старым сервером auth_request отклоняет запросы, а не открывает доступ.

Прокси сам задаёт `X-Codex-Public` и реальный IP клиента. Backend доверяет этим заголовкам только при loopback-соединении; они включают дополнительный запрет общего ключа и корректный учёт попыток регистрации по адресу клиента. Ограничения Nginx: 10 запросов/с с burst 30, подключение по коду — 3/мин с burst 3, 10 соединений на IP, тело до 1 MiB (приложение ограничивает до 1 000 000 байт), таймауты. Превышение частоты возвращает 429; агент сохраняет события и повторяет доставку. Заголовки авторизации и тела не включаются в access log.

HTTPS использует уже установленный сертификат IP `/etc/letsencrypt/live/nextcloud-ip/`; его продление и nginx reload выполняет существующий `nextcloud-certbot-renew.timer` и deploy hook. Это общая зависимость двух сервисов: её нельзя удалить вместе с Nextcloud без переноса продления. Самоподписанные сертификаты и отключение проверки TLS в агенте не используются.

Развёртывание: сначала установить сервер 0.4.2 штатным обновлением в простое; подготовить отдельный nginx site, проверить `nginx -t`, reload и только затем разрешить NAT. При предварительном включении site до обновления сервера доставка событий остаётся закрытой до появления внутренней проверки ключей. Изменение PUBLIC_URL вступает в силу после штатного перезапуска сервера. Проверять необходимо HTTPS, отказы для общего/неверного ключа, чужого machine_id и закрытых маршрутов, а также сохранение работы локального HTTP и Nextcloud. Проверка NAT loopback из дома не заменяет проверку из внешней сети.

Аварийное отключение внешнего доступа: отключить только правило NAT TCP 28443; локальный сбор и Nextcloud сохранятся. Порт 8765 напрямую в WAN не публиковать. Изменение Nginx/NAT не требует остановки сборщика статистики.

### Python-установка: запуск и ограничения

Код: `%LOCALAPPDATA%\CodexStatsAgent\releases\<версия>`, Python: `runtime\3.14.7`, выбранная версия: `current.json`. Данные остаются в `%APPDATA%\CodexStatsAgent`. Автозапуск — задача `CodexStatsAgent-<SID>` при входе текущего пользователя без повышения прав; если её создание запрещено, используется `CodexStatsAgent.lnk` в пользовательской автозагрузке, без VBS. Файловая блокировка исключает два новых сборщика одновременно. Фоновый `agent.log` ограничен по размеру.

Python закреплён на 3.14.7; автоматическое обновление самого интерпретатора пока не реализовано. ARM64/x86 пока не поддерживаются. Корпоративные политики могут запрещать Python и скрипты; установщик не отключает защиту. Authenticode для исходников не требуется, но подпись пакетов обязательна.

Прежний `agent/uninstall.ps1` отказывается удалять Python-установку, чтобы не стереть код работающего процесса. Для её удаления сначала штатно остановите агент, удалите его задачу/ярлык автозапуска, затем папку программы; папку данных сохраняйте.

Ручные команды после установки:

```powershell
$agentRoot = Join-Path $env:LOCALAPPDATA 'CodexStatsAgent'
& "$agentRoot\runtime\3.14.7\python.exe" -B "$agentRoot\launch.py" --version
& "$agentRoot\runtime\3.14.7\python.exe" -B "$agentRoot\launch.py" status
& "$agentRoot\runtime\3.14.7\python.exe" -B "$agentRoot\launch.py" stop
Start-Process "$agentRoot\runtime\3.14.7\pythonw.exe" -ArgumentList "-B `"$agentRoot\launch.py`" watch" -WindowStyle Hidden
```

`stop` запрашивает штатное завершение. Проверка без подключения, автозапуска и сбора: `bootstrap.ps1 -PrepareOnly -InstallRoot C:\Temp\CodexStatsProbe` (новая папка). `-ReleaseDirectory` принимает локальный **подписанный** релиз только в PrepareOnly; `-PythonArchive` — официальный ZIP с обязательной проверкой хеша. Не запускайте `watch` из проверочной папки вместе со старым exe 0.3.0: у старой версии ещё нет общей блокировки.

### Установка одной командой из Telegram

Администратор отправляет боту `/addpc` и получает одноразовый код (15 минут) и команду PowerShell. Установка под обычным пользователем Windows x64 автоматически разворачивает отдельный официальный Python Embedded 3.14.7, не меняя PATH и системный Python. Предварительная установка Python/Git и GitHub-токены не нужны.

Скрипт `agent/bootstrap.ps1` закреплён на теге `v0.4.2`. Он проверяет RSA-подпись релиза и SHA-256 `agent-source.zip`; для Python — закреплённый SHA-256 официального архива и подпись Python Software Foundation. После проверки путей и размера исходников подключает ПК по коду и запускает агент через `pythonw.exe` без консоли. Ключ ПК не разрешает управление сервером/регистрацию других ПК. Коды одноразовые, хранятся в виде хеша, число попыток ограничено; при потере ответа регистрации нужен новый код.

Адрес берётся из `CODEX_STATS_PUBLIC_URL` на сервере. Для домашней сети допустим `http://192.168.32.125:8765`; для интернета обязателен HTTPS. Сам скрипт не настраивает NAT, DNS или сертификаты. HTTP разрешён установщиком только для частных IPv4/loopback адресов и только в доверенной сети. Требуется действующая локальная авторизация Codex. Повторный запуск bootstrap при существующей конфигурации отказывается её перезаписывать: установленный агент обновляется автоматически.

Проверить подключение и версии можно командой `/updates`. Старый установщик с явным API-ключом ниже сохранён для совместимости и ручного восстановления. Установка версии 0.4.x поверх 0.3.x выполняется один раз в простое: старые версии не содержат автообновления.

Агент написан на стандартной библиотеке Python и может запускаться из исходников:

```powershell
py -m agent.codex_stats_agent configure `
  --server-url "http://192.168.32.125:8765" `
  --api-key "ЗАМЕНИТЕ_НА_ОБЩИЙ_СЕКРЕТ" `
  --user-name "Имя пользователя"

py -m agent.codex_stats_agent status
py -m agent.codex_stats_agent watch
```

Команда `status` проверяет локальную авторизацию и показывает текущий недельный процент. `watch` отслеживает только события, появившиеся после первого запуска, и сохраняет позиции файлов, активные задания и очередь недоставленных событий в `%APPDATA%\CodexStatsAgent`.

GitHub Actions проверяет код на Windows и Linux, а затем собирает один `codex-stats-agent.exe`. Для обычного push готовый файл доступен как artifact запуска workflow. Тег вида `v0.1.0` автоматически создаёт GitHub Release, после чего агент можно установить одной командой из корня репозитория:

```powershell
powershell -ExecutionPolicy Bypass -File .\agent\install.ps1 `
  -ServerUrl "http://192.168.32.125:8765" `
  -ApiKey "ЗАМЕНИТЕ_НА_ОБЩИЙ_СЕКРЕТ" `
  -UserName "Имя пользователя"
```

Установка не требует прав администратора: один `.exe` помещается в `%LOCALAPPDATA%\CodexStatsAgent`, а скрытый запуск при входе создаётся в пользовательской папке автозагрузки. Повторный запуск установщика обновляет exe, перезапускает агент и сохраняет постоянные `machine_id`, `machine_name` и путь к данным Codex.

Если репозиторий приватный, установщик автоматически использует сохранённую авторизацию Git Credential Manager. На компьютере без настроенного Git можно временно задать `GITHUB_TOKEN` с правом чтения репозитория либо предварительно скачать exe и выполнить:

```powershell
powershell -ExecutionPolicy Bypass -File .\agent\install.ps1 `
  -ServerUrl "http://192.168.32.125:8765" `
  -ApiKey "ЗАМЕНИТЕ_НА_ОБЩИЙ_СЕКРЕТ" `
  -UserName "Имя пользователя" `
  -ExecutablePath "C:\Downloads\codex-stats-agent.exe"
```

GitHub-токен используется только во время скачивания и не записывается в конфигурацию агента.

Удаление:

```powershell
powershell -ExecutionPolicy Bypass -File .\agent\uninstall.ps1
```

Локальная конфигурация специально сохраняется при удалении. В ней находится серверный API-ключ, поэтому файл `%APPDATA%\CodexStatsAgent\config.json` нельзя публиковать.

## Состояние установки

- Windows: основной вариант — отдельный официальный Python + исходники; совместимый exe может блокироваться Smart App Control.
- Orange Pi: сервер использует только стандартную библиотеку Python 3, SQLite и systemd; `pip`, Docker и отдельная СУБД не нужны.

## Сервер на Orange Pi

Скопируйте или клонируйте репозиторий на Orange Pi и выполните из его корня:

```bash
sudo bash server/install.sh
sudo nano /etc/codex-stats-bot.env
sudo systemctl enable --now codex-stats-bot
systemctl status codex-stats-bot
```

Обязательная настройка:

```dotenv
CODEX_STATS_API_KEY=длинный-случайный-секрет
```

Этот же секрет вводится в установщик каждого Windows-агента. Для создания секрета можно использовать:

```bash
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Для Telegram создайте бота через `@BotFather` и задайте `TELEGRAM_BOT_TOKEN`. Владелец проекта с Telegram ID `8461749755` задан начальным администратором через `TELEGRAM_ADMIN_CHAT_IDS`. Список доступа хранится в SQLite и сохраняется при обновлениях сервиса. Дополнительные ID из `TELEGRAM_ALLOWED_CHAT_IDS` импортируются как читатели при запуске; дальше ими можно управлять прямо в Telegram.

Администратор добавляет участника командой `/adduser CHAT_ID Имя`. Сам участник может заранее узнать числовой ID через `/whoami`, даже если доступа у него ещё нет. Команда `/users` показывает участников и кнопки удаления. Администратора, заданного в конфигурации, через бот удалить нельзя.

Команды бота:

- `/stats` — сводка текущего недельного окна по именам компьютеров;
- `/weeks [страница]` — вся сохранённая недельная история с навигацией и кнопками выбора;
- `/week N` — подробная статистика выбранной недели;
- `/active` — текущие задания;
- `/last` — последние завершённые задания;
- `/whoami` — Telegram chat ID для настройки доступа;
- `/users` — список участников и кнопки удаления, только администратор;
- `/adduser CHAT_ID [имя]` — предоставить доступ, только администратор;
- `/removeuser CHAT_ID` — отозвать доступ, только администратор;
- `/help` — справка.
- `/addpc` — одноразовый код и полная инструкция установки Windows-агента, только администратор;
- `/updates` — версия сервера, версии ПК и состояние обновления.

Все допущенные участники видят общую статистику проекта. Граница периода — сброс недельного окна Codex, включая внеплановый, а не календарный понедельник. Через `/weeks` и `/week N` доступна вся накопленная история. Строки подписаны именами компьютеров, стабильный ключ — `machine_id`; переустановка с сохранением конфигурации не создаёт новый ПК.

HTTP API:

- `GET /health` — проверка доступности без авторизации;
- `POST /api/v1/events` — события Windows-агентов;
- `GET /api/v1/stats?days=7` — текущие счётчики после последнего сброса; `history_observed_percent` отдельно суммирует исторические периоды за указанные дни (1–365).

Кроме `/health`, запросы требуют заголовок `Authorization: Bearer <CODEX_STATS_API_KEY>`. Повторная отправка одного `event_id` безопасна и не создаёт дубликат.

Исключение — `POST /api/v1/enroll`: он проверяет одноразовый код и выдаёт индивидуальный ключ ПК. `POST /api/v1/agent/checkin` принимает ключ своего ПК (либо прежний общий ключ для совместимости) и передаёт активность, длину очереди, версию и результат обновления. Индивидуальный ключ не позволяет отправлять события от имени другого ПК. `POST /api/v1/control/updates` доступен только с серверным ключом; им пользуется локальный привилегированный updater. `/health` дополнительно возвращает `version` и `maintenance`. Во время переключения сервера `/api/v1/events` отвечает 503: агент сохраняет события и доставляет их после возобновления приёма.

## Безопасное автообновление

Обновляются только опубликованные стабильные GitHub Releases, не каждый push. Релиз содержит `agent-source.zip`, совместимый `codex-stats-agent.exe`, `server.tar.gz` и подписанный `release.json`. Манифест подписывается RSA-3072/SHA-256 в CI ключом `RELEASE_SIGNING_KEY` из GitHub Actions Secrets. Закрытого ключа нет в Git, клиентах или серверном пакете. Открытый ключ закреплён в коде и bootstrap. Проверяются подпись, размеры, SHA-256, стабильный номер версии, протокол, схема и разрешение безопасного отката; автоматическое понижение версии запрещено. Первоначальное доверие к установочному скрипту основано на HTTPS GitHub и закреплённом теге.

### Простой и предупреждения

- Клиент отправляет check-in примерно каждые 15 секунд. Обновление разрешено только после 5 минут без активных заданий и без недоставленных событий. Пакет скачивается заранее, а перед установкой журнал перечитывается.
- Сервер ждёт 5 минут подтверждённого простоя доступных ПК. Недоступные ПК не считаются подтверждённо свободными: обновление разрешается только при совместимом протоколе, чтобы их очередь могла быть доставлена позже. Несовместимый агент блокирует автоматическое обновление.
- Бот предупреждает за 60 секунд. Начало задания или появление очереди отменяет подготовку. Если Telegram не смог доставить предупреждение, установка не начинается.
- Перед заменой клиент повторно проверяет журнал. Появились новые события — обновление отменяется. Уже запущенные задания Codex принудительно не завершаются.
- Нет абсолютной блокировки запуска Codex: если пользователь начнёт задание в короткий промежуток остановки агента, журнал будет дочитан после запуска, но точный снимок лимита «до» задним числом получить нельзя. В сообщении будет отсутствующий замер, а не выдуманный расход.
- Для автообновления долгое молчание задания не равно завершению: зависшая/неопределённая активная задача блокирует обновление. При старте агент сверяет сохранённые задачи с терминальными событиями и последующими заданиями в том же журнале; убираются только подтверждённо неактивные записи.

### Сохранность и откат

Конфигурация, machine_id, SQLite, позиции чтения и очередь находятся вне каталогов версий. Python-клиент заранее проверяет исходники и запуск, получает разрешение сервера, штатно завершает старый процесс и атомарно переключает `current.json`. Helper проверяет здоровье после успешного check-in. При отказе возвращается прежний код без отката данных. `pending.json` и независимая папка `recovery` обеспечивают возврат при следующем запуске после прерывания обновления. Если новый процесс не удалось штатно остановить, требуется ручное восстановление; принудительного завершения нет. Ошибочный релиз блокируется маркером в `%APPDATA%\CodexStatsAgent\updates`. Прежний exe-updater теперь тоже проверяет запуск кандидата до остановки старого агента.

Сервер обновляет отдельный root-owned `codex-stats-updater.timer`: проверка условий примерно раз в минуту, обнаружение новых релизов — раз в 15 минут. Непривилегированный HTTP-сервис не может заменять свой код. Версии размещены в `/opt/codex-stats-bot/releases`, активная версия выбирается ссылкой `current`. Перед переключением закрывается приём событий, создаётся согласованная SQLite-копия и проверяется запуск схемы на отдельной копии. После переключения проверяется `/health`. При неудаче возвращается предыдущая версия кода. Журнал транзакции и резервные копии — `/var/lib/codex-stats-updater`; отдельный recovery runner в `/opt/codex-stats-updater` переживает неработоспособную новую версию и продолжает откат после перезагрузки.

Старая база автоматически поверх рабочей не восстанавливается: это могло бы удалить уже принятые события. Автообновление разрешено только при неизменных совместимых схеме БД/состояния агента и протоколе (`schema=1`, `protocol=1`, `rollback_safe=true`). Несовместимые миграции требуют отдельной процедуры и повышения версии схемы, а не обхода проверки. Разработчик обязан проверить совместимость отката до публикации. Резервные копии и предыдущие каталоги не удаляются автоматически; за свободным местом нужно следить.

В `/etc/codex-stats-bot.env` добавьте:

```dotenv
CODEX_STATS_PUBLIC_URL=http://192.168.32.125:8765
CODEX_STATS_RELEASE_CACHE=/var/cache/codex-stats/releases
```

Для новой установки после настройки и запуска сервера включите таймер:

```bash
sudo systemctl enable --now codex-stats-updater.timer
systemctl status codex-stats-updater.timer
```

`server/install.sh` — начальная установка из доверенных исходников, не замена работающего сервиса в обход простоя. На существующем сервере переход к каталогу `current` и установка recovery runner выполняются один раз в согласованном окне простоя. Остановить автоматические обновления сервера можно через `systemctl disable --now codex-stats-updater.timer`. Для клиента неудачный релиз блокируется маркером; общий план обновлений виден через `/updates`.

Переход с 0.3.0 — отдельная администраторская процедура в простое: подготовить подписанный релиз и отдельный Python через `bootstrap.ps1 -PrepareOnly`, затем запустить исходники того же релиза с `legacy-upgrade --stage ПАПКА_РЕЛИЗА` и `CODEX_STATS_INSTALL_ROOT`, указывающим на стандартную папку агента. Helper передаёт подтверждения простоя; root-owned `activate_legacy` на Orange Pi должен быть подготовлен для того же релиза. Сервер ждёт 5 минут простоя и предупреждает за минуту, обновляется первым; клиент получает отдельное разрешение. Только при однократном переходе после резервной копии данных останавливаются процессы старого сборщика по точному пути (0.3 не имеет штатного выхода). Codex не завершается. При ошибке возвращается старый запуск; после успеха VBS заменяется ярлыком Python. Обычный bootstrap не перезаписывает существующую конфигурацию. Публикация релиза сама по себе не мигрирует старые устройства.

По умолчанию сервер слушает все сетевые интерфейсы на порту `8765`. В локальной сети агенты подключаются к `http://192.168.32.125:8765`.

Не пробрасывайте `8765` напрямую в интернет: обычный HTTP раскрывает общий API-ключ при перехвате трафика. Для внешнего доступа направьте TCP `80` и `443` с роутера на Orange Pi и поставьте Caddy перед сервером; backend после этого рекомендуется привязать к `127.0.0.1`. Домен должен указывать на внешний IP. Минимальный Caddyfile:

```caddyfile
stats.example.com {
    reverse_proxy 127.0.0.1:8765
}
```

В Windows-агенте тогда используется только `https://stats.example.com`. До настройки домена и HTTPS доступ оставлен локальным.

## Ограничения Windows-агента

- Автоматическое распознавание рассчитано на текущий JSONL-формат Codex Desktop/CLI и может потребовать обновления при изменении формата.
- Процент недельного окна обычно округляется, поэтому небольшое задание может дать `0%` при ненулевых токенах.
- Первый запуск не импортирует старые задания, чтобы случайно не отправить исторические данные.
- Для прямого снимка лимита необходима действующая локальная авторизация Codex; OAuth-токен никогда не включается в отправляемые события.

## Выпуск версии

После успешного CI создайте и отправьте тег:

```powershell
git tag v0.4.2
git push origin v0.4.2
```

Workflow проверяет Windows/Linux, собирает совместимый exe и архив Python-исходников, упаковывает сервер, подписывает манифест и публикует четыре файла. Без RELEASE_SIGNING_KEY публикация завершается ошибкой. Установщик и обновления требуют подписанные пакеты. Прежний `agent/install.ps1` предназначен для exe, а не Python-установки.

## Проверка

Все тесты используют стандартный `unittest` и не обращаются к реальному аккаунту. В набор входит end-to-end сценарий с двумя условными Windows-агентами, локальным HTTP-сервером и пересекающимися заданиями:

```powershell
py -m unittest discover -s tests -v
```

Ручная проверка текущей авторизации выполняется отдельно командой `status`.

Проверка HTTP-сервера после запуска:

```bash
curl http://127.0.0.1:8765/health
curl -H "Authorization: Bearer $CODEX_STATS_API_KEY" \
  "http://127.0.0.1:8765/api/v1/stats?days=7"
```
